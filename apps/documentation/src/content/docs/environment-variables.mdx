# Environment Variables

**Local values come from one command: `bun run env:pull`.** It reads a secrets provider
(Infisical by default), writes each kept app's `.env`, and is the only moment local
development talks to that provider. `bun dev` and the `db:*` scripts read the files it
wrote, so a provider outage blocks a refresh, never a working session.

Decision record: [ADR 0004](https://github.com/niway-dev/monorepo-template/blob/main/docs/adr/0004-env-pull-behind-one-script.md).
Reusable conventions: the hub's [Infisical playbook](https://github.com/csdev19/general-knowledge/blob/main/infra/infisical-secrets.md)
and [environment inventory](https://github.com/csdev19/general-knowledge/blob/main/infra/environment-inventory.md).

## Get your environment

1. Install the provider's CLI and log in. Infisical on macOS:
   `brew install infisical/get-cli/infisical`, then `infisical login`.
2. Link the repo once: `infisical init` at the repo root, then commit `.infisical.json`.
3. `bun run env:pull` (another environment: `bun run env:pull -- --env staging`).
4. `bun run dev`.

Never edit the generated files by hand; change the value in the provider and pull again.
Without a provider, copy each kept app's `.env.example` to `.env` and fill it in.

The pull is **all or nothing**. Every file is fetched and checked first; existing files are
replaced only if every target succeeds. A missing key fails the run with the key's name.
Files are written owner-only (`0600`).

## How it is built

| Piece              | File                                 | Change it when                   |
| ------------------ | ------------------------------------ | -------------------------------- |
| Command            | `scripts/env/pull.ts`                | rarely; it only orchestrates     |
| What is written    | `scripts/env/config.ts`              | an app gains or loses a variable |
| Provider contract  | `scripts/env/providers/types.ts`     | never, ideally                   |
| Infisical provider | `scripts/env/providers/infisical.ts` | a folder is added in Infisical   |
| Provider registry  | `scripts/env/providers/index.ts`     | a provider is added              |

A **target** is one file: its path, the **consumer** that may read the values, the keys it
requires, and an optional filter. The consumer is provider-neutral: Infisical reads it as a
tag; another provider can map it to a path, a project or a vault item.

Targets whose app directory does not exist are skipped, so `bun run customize` needs no
change here when it deletes apps.

### Adding a provider

1. Write `scripts/env/providers/<name>.ts` exporting a factory that returns an `EnvProvider`:
   `check()` fails fast with the fix (CLI missing, not logged in, not linked), and
   `fetch({ environment, consumer })` returns that consumer's values. Never print a value.
2. Register it in `scripts/env/providers/index.ts`.
3. Use it once with `ENV_PROVIDER=<name> bun run env:pull`, or make it the default in
   `scripts/env/config.ts`.

## Infisical layout

Environments: `dev` (and `staging` / `prod` when CI reads from Infisical too).
Folders group values by what a leak enables; tags name the consumer that needs them.

| Folder      | What a leak or edit enables                    |
| ----------- | ---------------------------------------------- |
| `/public`   | Non-credential configuration: URLs and origins |
| `/database` | Read and write access to the database          |
| `/auth`     | Forging sessions; signing tokens               |

| Tag                        | Consumer                                 |
| -------------------------- | ---------------------------------------- |
| `server-runtime`           | `apps/server-hono`, `apps/server-elysia` |
| `web-runtime`              | `apps/web-hono`, `apps/web-elysia`       |
| `fullstack-runtime`        | `apps/fullstack-fn-only`                 |
| `fullstack-convex-runtime` | `apps/fullstack-fn-and-convex`           |
| `mobile-runtime`           | `apps/mobile`                            |
| `mobile-convex-runtime`    | `apps/mobile-convex`                     |

A key needed by several consumers is stored once and carries several tags. An untagged key
is silently absent from every file, which is why the pull checks required keys by name.
The Infisical CLI cannot export folders recursively, so the provider reads the folders
listed in `FOLDERS`; a new folder must be added there.

## Variables by pattern

| Key                                                     | Folder      | Tags                                                              | Required by                                                                                          |
| ------------------------------------------------------- | ----------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                          | `/database` | `server-runtime`, `fullstack-runtime`, `fullstack-convex-runtime` | API and fullstack apps; also the `db:*` scripts, which read the API's `.env`                         |
| `BETTER_AUTH_SECRET`                                    | `/auth`     | `server-runtime`, `fullstack-runtime`, `fullstack-convex-runtime` | API and fullstack apps                                                                               |
| `CORS_ORIGIN`                                           | `/public`   | `server-runtime`                                                  | API: Better Auth `trustedOrigins` (the CSRF check on sign-in), not HTTP CORS. Include the web origin |
| `BETTER_AUTH_URL`                                       | `/public`   | `fullstack-runtime`, `fullstack-convex-runtime`                   | Fullstack apps. On the API it is optional and, when set (OAuth), must be the **web** origin          |
| `VITE_SERVER_URL`                                       | `/public`   | `web-runtime`                                                     | Client-server web apps: the API they proxy to                                                        |
| `VITE_CONVEX_URL`                                       | `/public`   | `fullstack-convex-runtime`                                        | Fullstack + Convex                                                                                   |
| `JWT_PRIVATE_JWK`, `JWT_KID`                            | `/auth`     | `fullstack-convex-runtime`                                        | Fullstack + Convex (`bun run generate:convex-jwt-keys`)                                              |
| `EXPO_PUBLIC_API_URL`                                   | `/public`   | `mobile-runtime`                                                  | Mobile (inlined into the bundle: never a credential)                                                 |
| `EXPO_PUBLIC_CONVEX_URL`, `EXPO_PUBLIC_CONVEX_SITE_URL` | `/public`   | `mobile-convex-runtime`                                           | Mobile + Convex                                                                                      |

The client-server **web** apps need only `VITE_SERVER_URL`: they proxy every auth and data
request to the API and never run Better Auth or open the database.
`DATABASE_URL_DIRECT` appears in the API's `.env.example` but no code reads it.

## Where each app reads its file

| App            | Reads                                                                         | When                                    |
| -------------- | ----------------------------------------------------------------------------- | --------------------------------------- |
| API Workers    | `.env`, auto-loaded by Wrangler (never a `vars` block in `wrangler.jsonc`)    | `wrangler dev`, runtime                 |
| Web apps       | `.env`: Vite inlines `VITE_*` into the client; the Worker side reads the rest | build and runtime                       |
| Mobile         | `.env`: Expo inlines `EXPO_PUBLIC_*`                                          | bundle time: restart Metro after a pull |
| `db:*` scripts | the API's `.env`, through `bun --env-file`                                    | each command                            |

Production values are not pulled: CI injects them as Wrangler secrets (see the deploy workflow).
Convex packages keep their own `.env.local`, written by `convex dev`.
